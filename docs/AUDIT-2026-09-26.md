# Snipflag: product, engineering, and growth audit

Date: 2026-09-26. Audited checkout: `9f4dd38`. This is an assessment and proposed roadmap, not an implementation record.

## 1. Verdict

Snipflag has a credible, focused product: capture several pieces of visual evidence, annotate them locally, and create one useful Linear issue. Its strongest foundations are the session model, per-image editing, shared editor/export rendering, local persistence, Rust-owned credentials/networking, and stable issue identity.

The best direction is **the fastest dependable desktop evidence-to-Linear workflow for people who report visual bugs repeatedly**. Reliability, first-use setup, clear reports, and recovery will matter more than adding many more drawing tools. This positioning is a recommendation, not a demonstrated market advantage.

Primary users: QA engineers, developers, designers doing implementation review, and product people reporting defects. Windows should remain the first runtime acceptance target. Mobile, a general project-management client, and a hosted screenshot platform remain outside the current product.

The product looks substantially more mature than its verification record. Green compilation and browser tests are useful, but release confidence still depends on native capture, credentials, shutdown, failure recovery, and real Linear tests.

## 4. Concrete findings

Priorities: P1 = next hardening work; P2 = important next-cycle work; P3 = later improvement. These are product priorities, not formal exploit severity ratings. No critical remote exploit was established.

### F01 — Emptying a saved draft can leave deleted content on disk (P1, source-confirmed)

`src/App.tsx:46` returns without saving when there are no images, title, or description. `src/store.ts:65` removes an image in memory. Start with a saved image-only draft, remove its last image, and the autosave now skips persistence; the prior saved session and image can remain and reappear after restart. Clearing a text-only draft has a similar path.

Fix: distinguish a never-persisted empty session from an existing session that became empty. Persist the empty state or intentionally delete that existing draft through a serialized persistence operation.

Acceptance: remove the final image/clear all text, restart, and verify old content does not return and obsolete image files are removed.

### F02 — Uncertain submission and subsequent edits can disagree with the real issue (P1, source-confirmed path)

`src/App.tsx:193` unlocks editing after submission errors. `src-tauri/src/linear.rs:167` saves the current retry snapshot before reconciliation; when an existing issue is found, `complete` associates that current local snapshot with the remote issue. If the first create succeeded but its response was lost, edits made afterward were never part of that issue.

Stable UUIDs help prevent a duplicate, but do not establish content equivalence. The current sent screen can therefore describe images/text that differ from the submitted revision.

Fix: persist an immutable submission revision with a hash, target workspace, exported-image revisions, and operation identity. Reconcile that revision before allowing replacement. Offer an explicit separate draft for subsequent edits. Do not silently update the remote issue or generate a fresh issue UUID on an ambiguous retry.

Acceptance: lose the create response, edit/restart/retry, and prove both one issue and accurate correspondence between its content and the local sent receipt.

### F03 — Tray Quit bypasses the pending autosave (P1, source-confirmed risk window)

Autosave waits 400 ms in `src/App.tsx:63`; `src-tauri/src/lib.rs:176` calls `app.exit(0)` directly. A recent edit or new capture can be lost when quitting before persistence completes. The save-and-hide button flushes, but that is a different path.

Fix: a quit handshake that freezes mutations, commits active text editing, flushes pending saves, and exits only after acknowledgment. Show a recoverable error if saving fails. Handle OS shutdown separately and keep the expected crash-loss window documented.

Acceptance: edit and immediately choose Quit; restart and recover the edit. Inject disk-full and verify no false saved/success state.

### F04 — Deletion failures are silently ignored (P1, source-confirmed)

`storage.rs:157` discards `remove_file` errors. `delete` removes the database row first. The UI can report that history was deleted while image files remain. Files left by saves that fail before a session row is committed can also escape `clear`, which enumerates session rows.

Fix: record pending cleanup, surface partial deletion, retry orphan cleanup, and constrain every cleanup to validated app-owned paths. Retain minimal deduplication receipts deliberately and explain that separately. Do not promise forensic deletion from backups or SSDs.

Acceptance: simulate locked/undeletable image files and a failed metadata commit; verify cleanup status remains visible until resolved.

### F05 — Pixelation of partially transparent images needs correction and an adversarial test (P1, source-derived risk; not runtime reproduced)

`render.ts:78` preserves averaged alpha; `render.ts:115` draws that output using ordinary source-over composition onto the original image already drawn by `flatten`. With semitransparent input, original per-pixel content can contribute underneath the averaged overlay. The existing pixelation test uses an opaque white source, so it does not exercise this case.

Fix: replace the covered region's pixels with the block result instead of blending over original detail; preserve the intended transparency deliberately. Define coverage for fractional coordinates, edges, overlaps, resizing, and later annotations. Keep true block averages and a minimum 12-pixel block. Preserve legacy redactions last; do not reintroduce the removed solid-redaction tool as an assumed requirement.

Acceptance: checkerboard/text/alpha fixtures must produce block-uniform covered pixels with no original within-block variation on copy, save, and upload exports. Test translucent and fully transparent pixels and boundaries.

Pixelation should never be marketed as guaranteed anonymization. The code comment claiming text and faces are unreadable is stronger than the evidence. Give users strength controls, a 100% preview, and an honest explanation.

### F06 — Thumbnails display the original image (P1/P2, source-confirmed)

`Filmstrip.tsx:21` and `DescriptionEditor.tsx:61` use `image.dataUrl`, the original. Annotations and pixelation are absent from those previews. This does not show that originals are uploaded, but it defeats a user's expectation that hidden details stay hidden throughout the visible workspace.

Fix: generate bounded thumbnails from the flattened current revision, cache by image/revision, and invalidate after edits. Reuse them for mentions and future history previews. Never show unprotected originals as a privacy-review fallback.

Acceptance: pixelate, switch images, open mentions, reload; previews consistently show the protected revision.

### F07 — Original images remain unencrypted locally (P2, disclosed design limitation)

This is already disclosed in Settings/README. Pixelation changes exports, not the original PNG stored in app data. OS backups can also retain originals.

Improve: storage usage display, explicit original-retention controls, purge-after-success option, and optional encrypted local drafts with an OS-keyring-protected key. Define recovery if that key disappears. An irreversible flatten-and-discard-original action would require clear user intent and would end undo for that original.

Encryption is a meaningful roadmap item, not a claim that currently disclosed plaintext storage is a hidden breach.

### F08 — Undo history is not durable; image removal is not undoable (P2, source-confirmed)

`store.ts:26` restores annotations but resets `histories` to `{}`. Switching images preserves undo while the app runs; restarting does not. Removing an image deletes its annotation history and does not enter a session-level undo stack.

Fix: bounded durable edit history, schema migration, and recoverable image removal. Use a deletion grace period/trash or explicit undo toast; a full snapshot per pointer sample is unnecessary.

Acceptance: reopen after a restart and undo an annotation; remove an image and restore its pixels, order, aliases, and annotations.

### F09 — Automatic draft restoration only checks the first history item (P2, source-confirmed)

`App.tsx:91` checks `sessions[0]`; if the newest item is sent, an older unsent draft is not automatically restored. `storage.rs:174` also limits history to 200 without pagination.

Fix: a dedicated query for the latest eligible unsent draft, explicit resumable/pending states, history search/filter/pagination, and a last-opened session preference.

### F10 — Retention can discard unfinished and uncertain sessions (P1/P2, source-confirmed policy)

`storage.rs:191` prunes by last saved database timestamp, regardless of sent status or unresolved submission. The Settings label says "not opened," but loading is not itself the native timestamp update; a later autosave may refresh it. Pruning runs at startup and on retention-setting changes, not continuously. Its errors are discarded in `lib.rs`.

Fix: separate draft and sent retention, protect pinned drafts and unresolved submissions, show what will be removed when shortening retention, and document last-modified semantics. Retained receipts alone do not provide a visible recovery UI once the session is gone.

### F11 — Partial uploads are not resumed (P2, source-confirmed)

`linear.rs:186` keeps upload results only in local variables. If image 8 fails, retry starts uploading from image 1. This is safe against using stale image revisions because everything is re-exported, but wastes time and may leave unreferenced remote assets.

Fix: durable upload progress keyed by workspace + image ID + flattened content hash; reuse only verified compatible uploads and respect storage lifetime rules. Never log signed URLs. Keep retries user initiated; do not create a background automatic upload queue.

Acceptance: fail on image 8/10, restart, retry; reuse valid prior revisions and re-upload any changed image. Show that some assets may already have reached Linear when a submission fails or is cancelled.

### F12 — Network behavior is safe but coarse (P2)

One `NetworkLock` covers metadata, login, refresh, and submission. Submission uses `try_lock`, so an unrelated metadata load can make Create fail with "another operation". Team options load three paginated collections serially; no explicit retry exists for a failed options load with the same team. The 50-page cap returns partial results as if complete. Each request builds a new HTTP client, losing a shared connection pool. Rate-limit handling gives a fixed generic wait message.

Improve: serialize token refresh/credential rotation separately; use a shared HTTP client; cancel stale metadata requests; cache metadata with age and workspace identity; provide retry and searchable selectors; report truncation; respect server rate-limit information. Any create retry remains governed by the durable submission state machine.

### F13 — OAuth onboarding adds major friction (P1 product work)

The default settings require a public client ID. Setup asks users to create a Linear OAuth app. This is acceptable for developer setup but a substantial barrier for an ordinary QA/designer user.

Ship an owner-managed public OAuth client ID in official installers, keep advanced custom-client setup for self-builds, and make the normal path one Connect Linear button. Test a fresh user with no knowledge of OAuth. Do not embed a client secret.

Current requested scopes are `read,write` (`auth.rs:104`). Linear documents `issues:create` for creating issues and attachments. Evaluate `read,issues:create` against all required operations in an authorized test workspace before narrowing scopes. A future comment feature may need `comments:create`. [Linear OAuth documentation](https://linear.app/developers/oauth-2-0-authentication).

The loopback page says "connected" before token exchange/keyring persistence finishes (`auth.rs:85`); change that to "Authorization received; return to Snipflag." Local disconnect deletes the credential but does not itself revoke the remote grant; clarify that behavior and evaluate explicit revoke support.

### F14 — Keyboard access stops short of full editing (P2)

The toolbar has useful names and shortcuts. However, region capture is pointer-based except full-monitor Enter, and canvas annotation selection/movement/resize lacks an equivalent keyboard workflow. The app suppresses browser zoom but has no independent UI scaling setting. Keyboard tool selection alone does not meet the product's broad keyboard acceptance statement.

Add an accessible annotation list, Tab/arrow selection, arrow-key nudge and Shift larger nudge, numeric geometry, keyboard crop/region controls, UI scale/text size, focus restoration, and screen-reader testing. Radio groups should follow consistent keyboard navigation. Test high contrast and 200% scaling as well as color contrast.

### F15 — Resource limits do not yet imply bounded runtime memory (P2, unbenchmarked)

The model keeps full base64 PNGs; all filmstrip originals may decode; Rust hydration loads every image; submit accumulates every flattened base64 export before sending. Imported batches are converted before the store checks session count/total. Capture checks encoded size but does not directly apply the 40MP limit before emitting a captured image.

Ten 40MP RGBA images alone would be about 1.6 GB if simultaneously decoded, before canvases, strings, history, and IPC copies. This is an upper-bound illustration, not measured app usage; the encoded-size limits also constrain which sessions are accepted.

Improve: check batch count before decoding, enforce common limits across capture/import/paste, bounded thumbnails, load originals on demand, release inactive decoded assets, avoid giant base64 IPC batches, and move CPU-heavy work off interaction threads. Measure before selecting a new rendering architecture.

### F16 — Storage robustness needs fault-focused work (P2)

Image writes use temp+rename, but there is no explicit image file sync before committing the SQLite reference. SQLite uses FULL synchronization, which does not itself sync a separately written PNG. Treat power-loss durability as unverified. Saves can leave orphan files when later validation/DB writes fail. Session schema version is fixed at 1; there is no migration framework. Annotation fields/point arrays are not exhaustively typed and validated in Rust. Loading trusts saved metadata and reads full files.

Add a versioned typed schema, finite-number and per-field bounds, migration backups, startup consistency scan, recoverable missing-image UI, and serialized session save/delete coordination. Distinguish process-crash recovery from sudden power-loss durability. This is hardening, not evidence of a demonstrated exploit.

### F17 — Some settings/native failure paths can become inconsistent (P2)

`save_settings` changes the shortcut and autostart before committing preferences. A later failure can leave runtime state different from saved settings. Tray setup failure is logged, while closing still hides the main window; that can strand users without an obvious reopen route. Capture monitor geometry/set-position failures are mostly ignored; a failed monitor capture aborts the entire grab.

Add rollback/reconciliation for settings; show tray unavailability and use a usable close fallback; make capture cancellation return to the prior visible/tray state; report monitor-specific limitations. Test hot-plug, sleep/wake, RDP, shortcut conflicts and keyring lock. These require native verification, not assumptions from compilation.

### F18 — Release, docs, and marketing are out of step (P1/P2)

Source 1.1.0 and the newer workspace imagery/features sit alongside the published 1.0.0 download. Signing/notarization and a verified updater remain absent. `publish-preview.yml` reads `docs/releases/v1.0.0.md` regardless of the version being published, so using it for 1.1.0 would reuse old notes. Existing same-SHA checks/build checks and checksum generation are good safeguards.

`docs/SECURITY.md` still recommends the removed redaction tool and says deleting a session removes submission records, while storage deliberately retains receipts. STATUS opens with an obsolete private-repository claim. The website calls the release a preview while GitHub marks it regular/latest after the owner's earlier override.

Fix the discrepancies; version release notes dynamically; publish explicit per-platform evidence and known limits. Do not publish a new release during this audit. Future stable releases should follow the current acceptance/signing requirements; the historical owner override is not new verification.

## 7. UX direction

The saved workspace screenshot shows a coherent evidence canvas with a dedicated composer. Preserve that visual identity and the owner's preferences: little repeated chrome, no hover movement, transparent text entry, and no solid-redaction tool.

Improve predictability before decoration:

- Let people resize or collapse the composer when inspecting large evidence; remember their choice.
- Show a compact visible saved indicator. Errors must persist until resolved; transient toasts are not enough for data loss.
- Display flattened thumbnails, report order, and image aliases consistently. Alias number and position can differ after reorder; distinguish them visually.
- Explain blocked Create actions beside the form and focus the first missing field.
- Offer a final report preview without adding a mandatory extra click to every experienced user's submission.
- Add contextual empty/loading/error/retry states for every selector and history view.
- Make destructive removal reversible, with shortcut and focus behavior that works inside dialogs.
- Keep optional details collapsed. Do not turn the composer into a full Linear issue editor.
- Prefer command search/help over adding every future action to the main toolbar.
- Restore sensible window size/monitor state and provide a native-control accessibility fallback if frameless controls prove troublesome.

A user should be able to answer: Which session is open? Is it saved? Which image am I editing? Which workspace receives this? What will leave my machine? Did it actually create an issue?

## 8. Engineering work that unlocks the roadmap

1. Introduce typed, versioned Rust session/annotation models and compatible frontend validation.
2. Add explicit durable states: draft, preparing, uploading, creating/unknown, sent, cleanup-pending. Separate user-editable drafts from immutable submission revisions.
3. Serialize save/delete/quit operations per session; protect against stale in-flight saves recreating deleted sessions.
4. Build a flattened-revision cache for export, thumbnails, and upload identity. Privacy transformations must be consistent at every destination.
5. Replace repeated full-image hydration/IPC where profiling demonstrates pressure; retain Rust ownership of filesystem and network access.
6. Inject transport/clock/storage dependencies for deterministic failure tests. Test doubles belong in tests, never as fake production success.
7. Add migrations with backups before storing durable history, crop derivatives, workspace profiles or upload manifests.
8. Make release publication version-aware, resumable after partial failure, and tied to exact verified source and signing evidence.
9. Add dependency/advisory checks, Rust clippy/format checks, frontend linting and immutable Action revision pinning on GitHub Actions. No vulnerability findings are claimed until such checks run.
10. Offer a local, inspectable support bundle with app/OS versions, error codes and timestamps. Exclude screenshots, freeform report text, credentials and signed URLs by default.

Record OS, architecture, display configuration, app revision, scenario, outcome and evidence. A green native compiler job is not a completed row.

## 10. Performance and success criteria

Proposed initial targets, not current measurements:

- Warm capture shortcut to selectable overlay: p95 under 500ms on a stated Windows reference machine; cold launch tested separately.
- Normal drawing: target a 16.7ms frame budget on that reference setup, with p95 interaction measurements.
- Save indication: normally durable within one second after edits stop; explicit flush for quit/submission.
- Zero duplicate issues in the deterministic retry matrix; zero false sent/deleted states.
- Zero privacy export mismatches in the adversarial fixture suite.
- First capture/annotation without sign-in; first issue without developer-console setup.
- Five unfamiliar target users can connect and submit a useful two-image report without coaching; record completion time and where they hesitate.
- A ten-image stress session remains interactive and returns near its baseline memory after close; set a concrete memory budget after measuring accepted worst-case inputs.

For product validation, observe report creation time, successful completion, missing information requested by developers, repeated weekly use, and use of multiple evidence images. Collect through consenting user sessions or optional counters without screenshot/report contents. Do not add silent screenshot analytics.

## 11. Distribution and trust

Near term: signed Windows releases, macOS signing/notarization, exact release notes, architecture-specific downloads, stable artifact retention, checksums, honest known-limit pages, and a clear support/security reporting route. Add a verified updater only with real signing keys, channel policy, draft-safe restart, and rollback planning.

Later: evaluate WinGet and other requested package channels, Windows ARM64 after demand and runtime validation, organization deployment presets, and localized onboarding. Existing MSI packaging is a useful starting point. None of these replace runtime tests.

The website should demonstrate the actual downloadable version. Explain the local-original/upload boundary, supported environments and setup requirements clearly. Prefer a few complete user workflows over expanding comparison pages. Do not claim fastest/safest/best or competitor absence without comparative evidence. Keep download, release status, screenshots and source versions aligned.

The app and website have different privacy surfaces: the website uses external font/CDN resources; desktop CSP excludes remote assets. A privacy statement should distinguish the two. No website performance score or conversion improvement was measured in this audit.

## 12. Recommended delivery sequence

### Phase A — Trust and correctness

Fix F01–F06, protect pending submissions from retention, add key failure tests, resolve stale security/release documentation. Exit only when the named regression scenarios pass remotely. Preserve existing aesthetics.

### Phase B — A first-time user can succeed

Owner-managed OAuth onboarding, visible save/recovery state, report preview, team defaults, searchable selectors, templates, delayed capture and active-window capture. Observe five representative users. Exit when they complete the workflow without setup coaching.

### Phase C — Dependable everyday use

Durable undo, recoverable image removal, history search/pagination, partial-upload resumption, memory work justified by measurements, keyboard editing, native acceptance, signing and draft-safe update design.

### Phase D — Distinctive evidence reports

Link numbered annotations to report steps, add evidence to existing issues, before/after comparison, metadata review, local OCR suggestions, and team presets. Validate each against real use before expanding further.

### Phase E — Optional expansion

Scrolling capture, multi-workspace profiles, encrypted drafts, additional tracker integrations, browser companion for optional context, and team administration. Prioritize based on repeated user requests, support cost, and evidence of retention.

Video, cloud AI, mobile apps, hosted galleries and a full Linear client are strategic expansions beyond current non-goals. Do not include them in a near-term implementation plan merely because competitors have them. If later validated, change PRODUCT deliberately and design the new privacy/permission boundary first.
