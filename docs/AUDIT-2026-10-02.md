# Snipflag: end-to-end product, UX and code audit

Date: 2026-10-02. Audited checkout: `de97087` (v1.3.0). This is an assessment and a proposed plan. **No application code was changed.**

How this was done: every file under `src/`, `src-tauri/src/`, the CI workflows and the project docs was read in full; `src/style.css` and `tests/app.e2e.ts` were scanned with scripts rather than read line by line. Nothing was built, installed or run (project rule: builds only on GitHub Actions), so there are **no measured numbers** here: no bundle size, no Lighthouse, no timings. Every finding is from the source. Items marked *verify* are my reading of the code and need a runtime check before acting.

The earlier audit ([AUDIT-2026-09-26.md](AUDIT-2026-09-26.md)) listed F01–F18. Most of its P1 items are fixed (empty drafts, immutable submission snapshots, quit handshake, deletion failures, pixelation compositing, protected thumbnails, durable undo, built-in OAuth client, report preview, templates, history search). What is still open from it is called out below as "carried over".

## 1. Product and user summary

**What it is.** A desktop tray utility (Tauri 2, Rust core, React editor) that turns one or more screenshots into a single Linear issue. Press a global shortcut, drag a region, mark it up (arrow, box, pen, highlighter, text, numbered steps, pixelate, crop), fill in title/team, and Create issue. Since 1.3.0 it is also useful without Linear: Copy image, Save image, and "Copy for AI" (writes flattened PNGs to `Pictures/Snipflag` and copies their paths plus notes).

**The problem it solves.** Reporting a visual bug normally takes about nine steps across three tools (capture, open an editor, annotate, save, open Linear, new issue, drag files in, type, pick the team). Screenshot tools stop at the image; Linear's own flow has no capture or mark-up. Snipflag joins the two and keeps several screenshots in one issue.

**Who it is for.** QA engineers, developers, designers reviewing implementation, and product people who file visual defects in Linear repeatedly. Windows first.

**Mindset on arrival.** They are in the middle of something else and have just seen a bug. They expect: shortcut, drag, image appears instantly, two or three marks, send, back to work. They want the screenshot never lost, the issue never duplicated, and private details hidden before anything leaves the machine.

**What makes them leave.**
- Capture feels slower than the Windows Snipping Tool.
- A report is lost, duplicated, or silently not sent.
- The shortcut does nothing with no explanation.
- Linear looks "disconnected" when they are only offline.
- Drawing lags on a 4K screenshot.
- An unsigned-installer warning at install time (known, outside this audit).

**Architecture map.**

| Layer | Where | Notes |
|---|---|---|
| Screens | One editor window (`src/App.tsx`), one overlay window per monitor (`src/components/CaptureOverlay.tsx`, `index.html?capture=N`) | No router. Dialogs: Settings (7 sections), History, Report preview |
| Components | `Toolbar`, `Editor` (Konva), `StepNotes`, `Filmstrip`, `IssuePanel` (+ `DescriptionEditor`, `LabelPicker`, `ReportPreview`), `EmptyState`, `Dialog`, `ColorPicker` | |

## 2. Core flows

Picked by entry-point prominence (there are no analytics): the global shortcut and tray menu, the empty state's three buttons, the always-visible toolbar, share bar and issue panel.

### Flow A: Capture (every session)
Evidence: global shortcut, tray "Capture screenshot", primary button in the empty state, "Capture" tile in the filmstrip.

1. Shortcut or tray → Rust `request_capture` emits `capture-requested` (`lib.rs:59`).
2. Editor `capture()` checks busy / locked / 10-image limit, flushes the draft, calls `start_capture` (`App.tsx:169`).
3. Rust hides the editor, waits for the compositor, optional delay, grabs every monitor, emits `capture-begin` (`capture.rs:189`).
4. Warm overlay loads the frame over `snipframe://`, shows itself, user drags (or Enter for the whole screen, Esc to cancel).
5. `capture_select` crops, optionally copies/saves, shows the editor, encodes PNG, emits `capture-complete`.
6. Editor adds the image, plays the shutter, flashes, sizes the window.

### Flow B: Mark up (every session)
Evidence: the toolbar is the first thing on screen once an image exists; default tool is Arrow.

1. Pick a tool (button or V/A/L/R/E/P/H/T/N/B/C) → drag on the canvas → mark is committed with an undo entry.
2. Select (V) to move, resize, nudge, duplicate, restyle, delete. Ctrl+Z / Ctrl+Shift+Z per image.
3. Autosave 400 ms after each change; filmstrip thumbnail re-renders.

### Flow C: Collect several screenshots (most sessions with a real bug)
Filmstrip: capture again, add files, paste, drop; click to switch; drag or arrow buttons to reorder; remove with "Put back" toast; caption under the canvas.

### Flow D: Create the Linear issue (the product's promise)
Evidence: the right-hand panel is open by default; Ctrl+Enter.

1. Title → Description (templates, `@image` mentions, step notes) → Team (remembered) → optional details.
2. Optional eye button → Report preview.
3. Create issue → save → flatten each image → `submit_issue`: identity check → upload each PNG → `issueCreate` with the session UUID → sent screen (Open issue / Copy link / New session).
4. Failure: error at the foot of the panel; an unknown outcome locks the report until "Check previous attempt".

### Flow E: Share without Linear (new in 1.3.0, likely frequent)
Share bar under the image: Copy image (Ctrl+C), Copy for AI (Ctrl+Shift+C), Save image.

### Flow F: First run / connect Linear (once, but it gates Flow D)
Empty state → capture → panel shows "Connect Linear" → browser OAuth → back to the app → teams load.

### Flow G: Come back later (restart, tray, History)
Launch restores the newest unsent draft; close button hides to tray; History dialog opens, searches, filters and deletes sessions.

### Long tail
Settings sections (templates, themes, capture options, retention, shortcuts reference, About/updates), custom colors, crop, snap guides, magnifier, adjust-selection mode, capture delay, save-every-capture, custom OAuth client (buried under Connection → Advanced, correctly), step notes panel (appears only after a step is placed), sound cues.

## 6. Optimization

No build was run, so gains are reasoned estimates, not measurements. Each item should be measured on Actions or on your machine before and after.

| ID | What | Location | Expected gain | Eff |
|---|---|---|---|---|
| O-01 | **Split the Konva scene into layers.** Today the screenshot, every mark, the draft stroke and guides share one `<Layer>`, and the draft is React state in `Editor`, so every pointer move re-renders all shapes and repaints the full image. Use a static image layer, a marks layer, and a small draft/guides layer. | `Editor.tsx:325-341` | The largest felt win: stroke latency on 4K captures with many marks. Per-move cost drops from "whole image + all marks" to "one stroke". | M |
| O-02 | **Thumbnails without a full re-flatten.** After each mark (80 ms debounce) the filmstrip decodes the full PNG again and redraws at full size on the main thread. Cache the decoded source per image and draw straight to a 160 px canvas, or copy from the Konva stage for the active image. | `render.ts:173-198`, `ProtectedThumbnail.tsx` | Removes a full PNG decode (tens to hundreds of ms on 4K) after every mark. | M |
| O-03 | **Stop stringifying undo history on every edit.** `boundedHistory` runs `JSON.stringify` over up to 512 KiB per edit, repeatedly while trimming. Track snapshot sizes incrementally. | `store.ts:7-13` | Removes a growing per-stroke cost in long sessions. | S |
| O-04 | **Async, single-pass exports.** `toDataURL` blocks the main thread; clipboard copy then base64-decodes and PNG-decodes in Rust only to get RGBA back. Use `canvas.toBlob` and send bytes (Tauri raw IPC), or send RGBA for the clipboard. | `render.ts:180`, `files.rs:29-37` | Copy image on 4K: no UI freeze; roughly one encode and one decode fewer. | M |
| O-05 | **One shared HTTP client.** `client()` builds a new `reqwest::Client` per request, so every call pays a fresh TLS handshake. A five-image submit makes 12 requests. Carried. | `auth.rs:50-53` | Likely 100–300 ms saved per request after the first; seconds on a multi-image submit. | S |
| O-06 | **Parallel uploads and one metadata query.** Screenshots upload one at a time; team options run three paginated queries in sequence. | `linear.rs:236-240`, `linear.rs:73-77` | Upload phase near 2–3× faster with three in flight; team pick feels instant-er. | S–M |
| O-07 | **Lighter autosave.** Every save sends the whole session with all undo histories, Rust re-validates it, rewrites the row, and scans the entire `images` directory for orphans. Scan only when the image set changed; store histories in their own column and write them less often. | `App.tsx:81`, `storage.rs:159-216` | Smaller IPC payload and no directory scan every 400 ms of editing; matters as History grows. | M |
